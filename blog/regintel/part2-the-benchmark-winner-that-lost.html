The benchmark winner that lost

RegIntel: answers you can check · Part 2 of 5

TL;DR — I compared Azure AI Search's built-in chunking with my own section-aware chunks on the same PDFs, with the same embeddings, planner and ranker. Mine won on every metric and kept the section numbers a regulatory citation needs: chunking mattered more than the pipeline. Then I tuned agentic retrieval's reasoning effort. minimal won my retrieval benchmark outright, and lost when I scored the answers. Benchmark what the user sees.

Part 1 was about checking answers. This part is about what they're built from: the passages.

A regulatory citation is a section, not a file

"EMA Guideline on the Investigation of Bioequivalence, §4.1.8, pp.14–15" is a citation a regulatory affairs person can use. "bioequivalence.pdf" is not. If the section number is going to appear in the answer, it has to exist before retrieval, so it has to come from chunking.

Regulators number their documents differently: FDA uses Roman numerals and letters (III.A.1), ICH uses decimals (4.1.1) and letter-decimals (A.2), the EMA's pharmacovigilance module uses paths (VI.B.7), and FDA Q&A guidances use Q4. One heading parser now recognises all six styles and nests them into a section path, and a chunk never crosses a section boundary. Each chunk carries its locator, its pages, and a one-line header naming its document:

[EMA · CPMP/EWP/QWP/1401/98 Rev. 1 · 2010-01-20] Guideline on the Investigation of
Bioequivalence — section 4.1.8 Evaluation

The header is embedded and keyword-indexed, so a passage always says whose rule it is. That was LegalMind's hardest lesson (right number, wrong document), applied from the start this time. The header is not part of the text quotes are verified against. The result was 1,869 chunks.

Azure can chunk for you. Should it?

Azure AI Search's new agentic retrieval offers a Blob knowledge source. You point it at a container of PDFs and it generates the whole pipeline: data source, skillset, index, indexer, chunking and embeddings. It's tempting. So I built both and compared them, holding everything else equal: text-embedding-3-large, the same gpt-5-mini planner, the same semantic ranker, effort low, and 42 questions.

* Approximate. Azure's chunks have no section field at all, so I had to infer their section by word overlap with mine. That footnote is the real finding: with integrated chunking an answer can cite the PDF, but not §4.1.8. And it cost more tokens.

What agentic retrieval actually does

A knowledge base puts an LLM in front of search. You send the question. The planner writes sub-queries, each runs as hybrid search (BM25 plus vectors, fused with Reciprocal Rank Fusion) with semantic re-ranking, and you get back passages and an activity log. Here is a real call, "Compare FDA and EMA acceptance limits for average bioequivalence":

StepWhat happened
Query planninggpt-5-mini: 964 tokens in, 106 out, 1.8 s; three sub-queries
Search ×350 candidates each from the section index
Ranking55,557 reasoning tokens (billed by the search service)
Top 3FDA statistical BE guidance · EMA §4.1.8 · FDA ANDA BE guidance

The planner split the comparison by regulator, as the knowledge base's instructions ask. That decomposition is the selling point: a comparison sent as one query tends to let one half fill every result slot.

The knob: reasoning effort

Each retrieval can set how hard the planner works. I measured three settings on two question sets: single and comparison questions (does the best section come first?) and ten multi-part questions (is every supporting passage in the top five?).

EffortSection hit@1 (42 questions)All passages found (10 multi-part)Seconds per query
minimal (no planner)0.8330.50.8
low0.7620.73.0
medium0.7140.910.7
Local hybrid, for reference0.8080.40.03

The columns disagree. On a precise single-document lookup the planner adds noise: it invented section numbers and added site:fda.gov to queries. It also costs seconds. On a question whose answer lives in three places, the planner is what finds the other two. So I'd route by question shape: medium for multi-part questions, and for single questions the obvious winner, minimal, which was the best and ten times faster.

The winner that lost

Then I scored answers, end to end, on all 70 questions, not just retrieval:

Single questions at…Fact recallUnanswerables declinedExpected source citeds / answer
medium everywhere0.9298 / 80.981~18
minimal0.8466 / 80.9629.2
low0.9338 / 80.98111.5

minimal put the best section first more often, but a complete answer needs the passages around the best one: the condition two paragraphs later, the exception in the next section. minimal ranked those lower, so answers lost facts. Worse, two of the eight unanswerable questions were answered instead of declined.

low matched medium's quality and was about 35% faster. That's what RegIntel runs.

The web made it worse

One more experiment. The Web knowledge source searches Bing, restricted here to fda.gov, ema.europa.eu, ich.org, ecfr.gov and the European Commission's health site. It found newer guidance my frozen corpus lacked. Mixed into the answering knowledge base, it made retrieval worse: section hit@5 fell from 0.942 to 0.885, and it made 48 Bing calls over 52 questions, despite an instruction to use the web only when the indexed guidance didn't cover the question. Web results are LLM-written summaries, never verbatim, so they can never pass the quote verifier.

The web now has its own knowledge base. It runs only after a decline, and it returns up to three regulator pages labelled "may help, not verified". It never supplies a citation.

Takeaways

  • Chunking is a design decision. It beat the managed pipeline on every metric and decided whether citations could name a section.
  • Agentic retrieval earns its cost on multi-part questions and hurts precise lookups. Route by question shape.
  • Benchmark the output the user sees. The retrieval winner lost on answers.
  • More sources are not more evidence. Text you can't verify belongs in a pointer, not a citation.
