An agent is a cost, not a feature

RegIntel: answers you can check · Part 4 of 5

TL;DR — Some regulatory questions need data, not documents: adverse-event counts from FDA's FAERS database, codes from CDISC terminology. A Microsoft Agent Framework agent answers them with four tools, and every number comes from DuckDB, never from the model. Then I ran the agent on the guidance questions too. It was slower, cost more, and was no better. A one-call router now sends each question to the cheapest path that can answer it.

Questions documents can't answer

"Is there a disproportionality signal for dupilumab and conjunctivitis in FAERS? Give the reporting odds ratio and its 95% confidence interval."

"Which CDISC SDTM codelist holds the values for a subject's sex?"

No guidance document contains these answers. The first is a computation over adverse-event reports. The second is an exact lookup in a 67,192-term vocabulary. A language model asked either will produce something plausible, and in pharmacovigilance plausible is the problem.

Data as tools, numbers from code

I loaded one quarter of FAERS (openFDA's 2025 Q1 release, parts 1–3: 36,000 reports). Each 900 MB JSON file is streamed into three Parquet tables (reports, drugs, reactions), about 3 MB in total, and queried in-process with DuckDB. CDISC Controlled Terminology comes from NCI EVS as tab-separated files, indexed for exact matching.

The agent gets four tools:

ToolDoesGuarantee
search_guidanceOne knowledge-base retrieval (Part 2)One call per sub-question
lookup_cdisc_termExact CDISC lookupA near-miss code is a wrong code, so: exact or nothing
faers_drug_summaryReports, serious, deaths, top reactionsBuilt from DuckDB expressions; the model never writes SQL
faers_disproportionalityThe 2×2 table and the reporting odds ratio with its 95% CISays, in its own output, that it is a screening statistic, not causation

The important design decision is what the agent is not allowed to do: write the answer. It plans and calls tools. Every result goes into a numbered evidence pool, and then the same writer, verifier and reviewer from Parts 1 and 3 answer from that pool. So a FAERS number in the answer has to appear in the FAERS tool's output, quoted. A real answer from the deployed API:

Reporting odds ratio for DUPILUMAB and 'Conjunctivitis' is 13.97 (95% CI 7.98 to 24.47). [1]

The passage cautions that disproportionality is a signal-screening statistic and "does not show that the drug causes the reaction." [1]

[1] openFDA FAERS extract, 2025 Q1 (parts 1-3) · computed

That's one tool call, 0.02 seconds in DuckDB, and 11.3 seconds end to end. If the writer had rounded 13.97 to 14, the verifier would have removed the statement. The caveat is in the answer because it's in the tool's output; the tool, not the prompt, makes it impossible to quote the number without it.

The caveat matters. For dupilumab, the reaction with the highest ROR in this data is atopic dermatitis (176), the condition dupilumab is prescribed for. A signal statistic finds things to look at. It doesn't explain them.

Making the agent cheap

The first version worked and was slow: 52.7 seconds of research, five tool calls, 32,000 tokens. Two of the calls were guidance searches for facts that live in FAERS or CDISC. Three changes fixed it:

  • Low reasoning effort. Planning tool calls is not hard thinking.
  • Parallel tool calls. Independent lookups run in one turn.
  • One sentence in the instructions: each source is only in its own tool. The guidance corpus has no FAERS data and no CDISC terms.
First runTuned
Research time52.7 s13.9 s
Tool calls53
Tokens32K4.5K

On the ten tool questions, with FAERS ground truth computed from the Parquet tables at evaluation time so it can't drift: all facts correct 10/10, right tools 10/10, wasted searches 0, at about a quarter of a US cent per answer.

Parallel tools brought one bug. Concurrent FAERS calls hit a single DuckDB connection and crashed with ResourceInUseException, which I found by clicking around the UI. A lock fixed it, and a 32-thread unit test keeps it fixed.

Then I gave the agent everything

If the agent can decompose questions and search guidance per sub-question, why not send all questions through it? I ran it on the 60 guidance questions and compared it with the fixed pipeline from Parts 1–3:

Expected source cited0.9810.923

No better on any measure, and 50% more expensive. Doubling its passages per search made it more expensive still ($0.0055) and no better. On questions whose steps are known in advance, the agent's flexibility bought nothing.

The router

So each question now gets one cheap classification call first (gpt-5-mini, minimal reasoning, about 1.3 s, structured output with two booleans):

  • Needs FAERS or CDISC data? Send it to the agent.
  • Guidance, several parts? Send it to the pipeline, with retrieval at medium effort.
  • Guidance, one question? Send it to the pipeline at low effort.

The prompt draws one line carefully. A question about safety reporting rules is a guidance question; a question that needs a FAERS count is a data question. If the output can't be parsed, the router falls back to the most capable path.

The router was accurate on 0.957 of 70 questions. Data questions went to the agent 10/10, and guidance questions went to it 0 times. The three misses were single-vs-multi borderline cases, where both paths answer anyway. End to end, the routed system matched the best fixed configuration on quality, was about 35% faster on single questions, and was the only configuration that could answer the data questions at all.

Follow-ups, without leaking

One more conversation feature, and one more mistake. "And for narrow therapeutic index drugs?" means nothing to retrieval on its own, so a rewriter turns follow-ups into standalone questions. My first version showed it the previous answers as well as the questions. The follow-up evaluation caught the leak: answer text was copied into the rewritten question, so retrieval found passages matching the previous answer, and the score went up for the wrong reason. The rewriter now sees earlier questions only. All 8 rewrites resolved, and 0 facts leaked.

Takeaways

  • Numbers must come from code. Let the agent choose tools, but not write the figures.
  • Separate research from writing, so one verifier guards every path.
  • Tool descriptions are prompts. "Each source is only in its own tool" removed every wasted call.
  • An agent is a cost, not a feature. Measure it against the pipeline; route to it only where it's needed.
  • Check your evaluation for leaks. A score that rises for the wrong reason is worse than one that falls.
