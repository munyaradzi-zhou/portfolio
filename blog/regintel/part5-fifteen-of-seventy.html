15 of 70: the bug only Azure could show me

RegIntel: answers you can check · Part 5 of 5

TL;DR — RegIntel was deployed on Azure Container Apps, with every unit test and the smoke test green. Then I sent it the 70 evaluation questions over HTTPS, one at a time, and 15 failed with "service is starting". Each question was blocking the server's event loop for about 16 seconds; the health probes timed out and Azure restarted the container mid-run. Two small changes took it to 0 out of 70, and the median latency fell by a quarter. Then the first continuous-deployment run failed three times for three unrelated reasons. The lesson both times: the real platform is part of the system under test.

Green everywhere

By the evening of the deployment, RegIntel had:

  • 185 unit tests at over 85% coverage, plus strict types, lint, security scans and a full-history secret scan in CI.
  • Infrastructure in Bicep: managed identity everywhere, keys only in Key Vault, Cosmos DB for sessions.
  • A deployed API and UI, and a smoke test that passed: health 200, ready 200, 401 without a key, one correct cited answer.

The local evaluation numbers were good. The question I hadn't answered was whether the deployed system gives the same answers, and how fast. So I wrote a live evaluation: the 60 golden questions and 10 tool questions, sent over HTTPS one at a time, exactly as a client would, scored with the same rules as the local runs, with latency measured at the client.

15 out of 70

It came back with 55 good answers, close to the local quality, and 15 HTTP 503s: "The answering service is starting."

That message comes from one place in the code: a request that arrives before the service has finished building at start-up. But the service had been running for an hour. The 503s came in two blocks of fast failures (0.3–0.6 s each), separated by long runs of normal answers. It looked like the container was restarting, twice, in the middle of the run.

What the platform saw

The answer wasn't in my application logs. It was in the platform's system log, in the environment's Log Analytics workspace:

Readiness probe failed: Get "http://100.100.0.213:8000/readyz": context deadline exceeded
  (Client.Timeout exceeded while awaiting headers)
Liveness probe failed: Get "http://100.100.0.213:8000/healthz": context deadline exceeded
Liveness probe failed: ...
Liveness probe failed: ...
Container api failed liveness probe, will be restarted

/healthz returns {"status": "ok"}. It does nothing. Why would it time out?

Because it couldn't run. FastAPI serves async routes on a single event loop. My /v1/ask route was async, but the code inside it was synchronous: OpenAI SDK calls, Azure AI Search calls, the Cosmos DB save. While one question took 16 seconds, those calls held the loop, and nothing else ran, including the health endpoint. Azure's probes use a 1-second timeout by default. After three liveness failures in a row, the platform did exactly what it should with a process that doesn't answer: it restarted it. Requests during the restart met the "starting" path.

The bug was mine, not Azure's. But only Azure could show it to me.

The fix

Two changes:

# before: blocks the event loop for the whole model call
decision, usage = self.router.route(question)

# after: runs in a worker thread; the loop stays free for probes and other requests
decision, usage = await asyncio.to_thread(self.router.route, question)

The same change went in for every blocking step: both pipelines, the web lookup, the follow-up rewrite, the session save, and the agent's writer and reviewer. The probe timeouts also went from 1 s to 5 s. That's not a fix on its own, but a margin.

The median latency also dropped by a quarter. I can't fully separate that from model-latency variance between the two runs, an hour apart, but probes and telemetry no longer queueing behind a blocked answer is a plausible part of it. The four answerable misses each failed closed, with a decline or a withheld answer, never an unsupported one.

Why the tests didn't catch it

The unit tests call the API one request at a time, with fakes for every model. There are no concurrent health checks and no platform that kills slow processes. Everything the bug needed (real latency, a probe with a timeout, a supervisor that restarts) existed only in Azure. The smoke test passed too, because one request at a time is exactly what it sends.

The live evaluation is now part of a release, not just of a write-up.

Deploying without a secret, at the fourth attempt

Then I pushed the code to GitHub and turned on continuous deployment. A workflow builds the images after CI passes, rolls out new revisions and runs the smoke test. It signs in to Azure with OIDC: GitHub issues the run a signed token naming the repository and branch, Entra ID trusts that exact subject on one managed identity, and no Azure secret is stored in GitHub at all. The identity can push images, update two apps and read one key, and nothing else.

The first run failed. So did the second and the third:

One thing worked first time, because I'd seen it coming. The apps live in another project's Container Apps environment: a free trial allows one per subscription. Updating an app re-checks a join permission on its environment, so the deploy identity has a custom role holding exactly that one action, on that one environment.

None of the three failures was visible by reading the YAML. Each took a minute to fix once it was visible.

Takeaways

  • In an async server, blocking calls freeze everything, health checks included. Use async clients, or move the work off the loop.
  • Evaluate the deployed system. Real traffic on the real platform found what 185 tests and a smoke test couldn't.
  • Know where each kind of log lives. The answer was in the platform's system log, not mine.
  • The first run of a pipeline is a test of the pipeline. Plan for it to fail, and read the error: AADSTS700213 prints the subject you need.
  • Least privilege is a list you discover. AcrPush needed Reader; the borrowed environment needed join.
