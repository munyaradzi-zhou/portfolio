The gate that caught what I would have shipped

LegalMind on Azure · Part 6

TL;DR — I added three things a legal assistant needs before anyone trusts it: an evaluation gate on every pull request, document-level access control, and live Dutch law. The access control held: 340 searches by five test users, zero leaked passages. The live-law tools worked: eight of eight answers cited the official text. And then the gate caught something none of my unit tests could: the research agent had found a real, anonymised court ruling and presented it as a named client's own case. The answer was labelled grounded, because the ruling really did say what the answer said.

Parts 1 to 5 ended with numbers measured once, by hand, on one evening. That's a snapshot, not a safeguard: the next prompt change could undo any of it, and I'd find out from a user.

A gate that runs the evaluation on every change

The evaluation suite already existed. What was missing was running it every time something changes, and comparing with what we had.

So the golden sets grew: 68 retrieval questions with the passage that answers them, and 66 questions for end-to-end answers, 14 of them unanswerable, including the near-misses from Part 4 whose answer exists in the documents but for someone else. A GitHub workflow starts the branch's API against the dev environment, runs both suites (about 25 minutes, so only on pull requests labelled run-eval), and compares each metric with a baseline recorded from main.

Each metric has a tolerance. Fact recall may wobble by a couple of points between runs; the LLM judge's groundedness score is too noisy to gate on at all, so it's reported, not gated. One row has no tolerance: unanswerable questions declined or flagged. Answering one confidently, without a warning, is never acceptable, however good the average is.

Who may see this passage?

A law firm's documents aren't one pool. A lawyer may see the files of the matters she works on, paralegals may not see privileged documents, and everyone may see public law. A retrieval-augmented assistant has to enforce that in retrieval: once a passage is in the model's context, it can surface in the answer, a citation or an excerpt.

Every chunk in the index now carries the groups allowed to see it. Users sign in with Entra ID; their token carries their roles (Lawyer, Paralegal, Admin) and their matter groups; and the search engine adds a filter to every query, failing closed when it can't determine who's asking. The alternative, Azure AI Search's built-in document-level permissions, is in preview, and it trims on user and group IDs only, while "paralegals don't see privileged documents" is a rule about a role. A security boundary shouldn't rest on preview behaviour, so I built the filter and wrote down why in ADR 0001.

Then I tried to break it: five test users (three lawyers on three different matters, a paralegal on the matter with a privileged case summary, and a guest on no matter at all) ran 340 searches across all matters and roles. Zero passages leaked. And 41 questions from an outsider produced zero citations of documents they couldn't see. The demo that convinced me, though, was simpler: the same user, the same question, before and after being added to a matter. The answer changed.

Live law

Uploaded copies of legislation go stale. So the research agent got tools for the official sources:

  • get_article("BW", "7:271") finds the version of Burgerlijk Wetboek Book 7 that is valid today through the government's search service, downloads its XML once, and returns the article per paragraph with the date its wording took effect.
  • search_case_law and get_ruling use rechtspraak.nl's open data. Its API filters by court, area of law and date, but has no full-text search, so the tool fetches up to a thousand recent rulings for the filters and ranks their official summaries itself.

Each result gets the next source number after the retrieved passages, [9], [10], is cited with its identifier and a link, and goes through the same groundedness check as everything else.

The first live answer came back labelled not_grounded. The groundedness check read only the first 8,000 characters of context, and eight retrieved passages already filled them: the live article sat after the cut-off, invisible to the judge. Live sources now come first, and the limit is 24,000. After that: 8 of 8 live-law questions cited the official source, named the article or ECLI, contained the expected facts and were labelled grounded.

The catch

Then the gate ran on the pull request. Retrieval: fine. Facts: fine. One row was red:

metric main this PR
Unanswerable: declined or flagged 1.000 0.929 FAIL

One question out of fourteen:

"Welke billijke vergoeding heeft de kantonrechter aan Eva Kramer toegekend?" — What fair compensation did the cantonal judge award Eva Kramer?

Eva Kramer is a client in the case files. Her employment dispute has a draft settlement agreement, not yet signed. No judge has ruled on it. Before live law, LegalMind's answer was flagged not_grounded, which counts as safe. Now it said:

"De kantonrechter heeft aan Eva Kramer een billijke vergoeding toegekend van € 4.000,- bruto. Dit blijkt uit de uitspraak van de Rechtbank Rotterdam (ECLI:NL:RBROT:2025:1815) …"

That ruling is real. It is about an unjustified summary dismissal, and it awards €4,000. It is also anonymised, like every published Dutch ruling: it names no employee. The agent had searched for case law, found a ruling that matched the facts it knew about Kramer, and stitched the two together. The groundedness check saw a claim, "€4,000 fair compensation", and a source that supports it, and said grounded.

Every individual step was correct. The tool returned a real ruling, the citation was real, and the check verified a claim that really is in its source. The error was in the link between them, and only a question written to have no answer could expose it.

The fix was small: every ruling the tools return now starts with "Geanonimiseerde uitspraak: the parties are not named. Not the case of anyone in the user's documents unless those documents cite this ECLI," and the research prompt says to call a similar case a precedent. The next gate run: 14 of 14.

Reading a red gate

Not every red row is a regression, and a gate is only useful if you read it:

  • On an earlier pull request the same row failed on a different question. The answer there was fine; the judge's definition of "declined" was too narrow. I fixed the definition, not the app.
  • On this one, two retrieval rows were red as well. That wasn't the change at all: the semantic ranker's free monthly quota had run out that morning (it also took search down on dev for a while: Part 7), and the baseline had been measured with it.
  • And one honest admission: the pull request was merged before the gate finished. The fix went out as the next one. A gate that isn't a required check is advice.

Takeaways

  • Run the evaluation on every change that can move it, and compare with a baseline, not with your memory.
  • Give "never acceptable" metrics zero tolerance; gate noisy ones loosely or not at all.
  • Enforce access in retrieval, and test it like an attacker: many users, every matter, count the leaks.
  • A grounded answer can still be wrong: every step can be right and the link between them invented. Only test questions that should fail will show it.
  • Read a red gate row by row. Make the gate required, or it's advice.
